# Questionnaire format and data model

- **Status:** proposed · **Date:** 2026-11-13 · **Involved:** @StellaBellange, @justingebert · **Ref:** #136, #45
- **Decision:** A template has `id`, `version`, `title`, `tags`, `questions` and an optional `scoring`. Answer types are `select-one`, `select-multiple`, `number` and `yes-no` (with `safety: true` for a safety question). There is no free text. A new type is one more entry in the shared schema. Scoring: `sum` lists the questions whose option points add up to the score, each question once. Without `scoring` a questionnaire has no score. There is no traffic light, a threshold for "problematic or not" can be added later. The schemas are in `packages/shared/src/questionnaires`. In the database, `questionnaires` (one row per questionnaire) has many immutable `questionnaire_versions` (the questions and scoring as JSON), a `scheduled_questionnaires` row is account, questionnaire and `due_at`, and a `questionnaire_responses` row holds the `answers` as JSON and the `score`. Both tables with account data reference `accounts.id` as `account_id` with `onDelete: "cascade"` (0020). A response also stores `questionnaire_id`, so that two foreign keys can check it: the version belongs to that questionnaire, and a scheduled questionnaire it answers has the same account and questionnaire. A change is a new version row, answers point to the version they were given on.
- **Why:** The questions are JSON, so a new answer type needs no migration. Versions that are never updated keep every old answer readable. A scheduled questionnaire has no status column: it counts as answered once a response points to it and as due once `due_at` has passed, so nothing can contradict itself. It points to the questionnaire, not to a version, so a due check-in uses the newest version at that moment. The score is stored with the response, a history needs no recalculation. Deleting an account deletes its schedule and answers. An answered scheduled row cannot be deleted on its own.
- **Rejected:** A `kind` (`check-in` or `screening`) on templates (it came from the old offer, there is one type of questionnaire for now, it can come back as a new field). One table row per answer (more rows and joins, the answers are read as a whole). One column per question (a migration for every change). A stored status or `completed_at` on scheduled questionnaires (can disagree with the responses). Free-text answers. A traffic light result (the offer is outdated, the ticket drops it).
- **Caution:** Which files hold the templates and how they are loaded into `questionnaire_versions` is #137. Checking answers against a template and calculating the score is #138. Points come from the source of each questionnaire and need to be confirmed by someone qualified. The ISI in the tests is an example only, its licence is open. A scheduled questionnaire has no link to an incident yet, add it with #44. The `answers` column holds health data: never log it.
