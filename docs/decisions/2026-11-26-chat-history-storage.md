# AI chat history: one row per message on the server

- **Status:** proposed · **Date:** 2026-11-26 · **Involved:** @tpiwko · **Ref:** #154
- **Decision:** Each account has one chat. Its messages are stored in `chat_messages`, one row per AI SDK `UIMessage` (`id`, `account_id`, `role`, `parts` as JSON, `created_at`). `account_id` references `accounts.id` with `onDelete: "cascade"` (0020). The frontend sends only the new user message (text parts only) plus the catalog, and the backend loads the history itself. A turn is saved in two steps: the user message when the request arrives, the reply in `onEnd` of `toUIMessageStream`, only if it completed. Separate inserts give the two rows different `created_at` (`now()`), which is the sort order. Reply IDs come from the server (`generateMessageId`), so browser and database use the same ID. A retry resends the same user message, and the known ID is skipped. All messages are kept. The chat shows the newest 50, the model gets the newest 10.
- **Why:** The history survives a new device session and Safari's `localStorage` wipe, and it goes with the account. The server does not trust history from the client, so a client cannot invent earlier replies. One row per message follows Vercel's AI chatbot and the AI SDK persistence guide: inserts only, "the newest N" is one `ORDER BY … LIMIT`, and IDs need no coordination. A message is small, so keeping everything costs nothing, and the `LIMIT` bounds both the display and the tokens per request.
- **Rejected:** Local only (`localStorage` or IndexedDB: lost after 7 days in Safari, no cascade, client-controlled history). One row per account with a JSON array (rewrites the whole chat each turn, two tabs can overwrite each other). Saving question and reply in one insert (both get the same `now()` and can swap places), and fixing that with a `seq` identity column or timestamps set in code. A rolling summary of older messages (an extra model call per turn, can drift from what was said). Deleting messages beyond a cap inside the save. Validating the stored history with `validateUIMessages` (only matters when the tool schema changes, test data can be wiped).
- **Caution:** A reply that breaks off (app closed, model error) is not saved, so the question stays unanswered: the chat shows a "try again" hint under it, and the model then gets two user messages in a row. `consumeStream()` does not help, because `onEnd` fires on disconnect with the partial reply. The model's last 20 can start with a reply. A change to `show_material`'s input or output can break old rows: empty the table.
