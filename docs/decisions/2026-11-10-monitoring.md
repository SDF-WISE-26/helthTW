# Monitoring on the prod-vm

- **Status:** accepted · **Date:** 2026-11-10 · **Involved:** @Lezhor, @LilGravyyyy · **Ref:** #152
- **Decision:** Dozzle shows container logs and resource use on the prod-vm. It runs as its own Compose project in `/srv/monitoring`, apart from `deploy.sh`, and only listens on `127.0.0.1`. Devs reach it through an SSH tunnel as the user `monitoring`: keys only, added by an admin, and nothing allowed but tunnels to the monitoring ports. Dozzle has no login of its own. It reaches Docker only through `socket-proxy`, which lets reading requests through and nothing else. Images are pinned by digest, analytics and update checks are off. Setup in [`deployment.md`](../deployment.md#monitoring).
- **Why:** The logs may contain health data. SSH already limits who can reach the VM, so there is no firewall change and no extra password. Devs need no account of their own on the VM. Access to the Docker socket is effectively root: through the proxy, a compromised Dozzle can read logs, but not start, stop or exec into containers. A broken monitoring setup cannot block a deploy.
- **Rejected:** A port for the HTW network with Dozzle's own login (firewall change, passwords to manage, reachable for all of HTW). An account on the VM for every dev (more rights than reading logs). Mounting `docker.sock` read-only (`:ro` only protects the file, not the API behind it). Dozzle Cloud or a hosted log service (data leaves the VM). A log stack like Loki and Grafana (several services and storage for a prototype).
- **Caution:** Dozzle only shows what Docker keeps (3 × 10 MB per container), there is no history. Every key on `monitoring`'s list can read all logs, remove keys of people who leave. Everyone who can log into the prod-vm can open Dozzle too. Never connect Dozzle Cloud. Changes to `deploy/monitoring/compose.yml` are installed by hand, a release does not do it. VM trends with Beszel follow in #152.
