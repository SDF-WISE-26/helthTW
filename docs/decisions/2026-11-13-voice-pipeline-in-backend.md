# Voice pipeline with LiveKit as a second backend entrypoint

- **Status:** proposed · **Date:** 2026-11-13 · **Involved:** @xavierwelscher · **Ref:** #86
- **Decision:** Voice is a chain of speech to text, LLM and text to speech on LiveKit Agents for Node (`@livekit/agents`) in the backend module `modules/voice`. The worker runs as its own process from the same package and image (`dist/voice-worker.mjs`). `POST /api/v1/voice/sessions` hands out a token for a fresh room and dispatches the agent by name, so the worker only joins rooms created by the backend. The LLM stage is our own adapter (`providers/llm.ts`) around the same AI SDK model as text chat, LiveKit keeps turn-taking, interruptions and history. The chat connects with `livekit-client` and shows the transcripts as chat messages. For the proof of concept: LiveKit Cloud, ElevenLabs (Scribe realtime, Flash TTS), Silero VAD, turn detection running locally, no session recording. Requirements in [`specs/voice.md`](../specs/voice.md).
- **Why:** One package shares env validation, schemas and the LLM setup with text chat, so voice can't drift from it. A separate process keeps audio load and crashes away from the API. Our own LLM stage keeps the reply text in our code, which is where a check has to sit before anything is spoken. LiveKit Cloud needs no TURN or media server of our own, self-hosting `livekit-server` later only changes the `LIVEKIT_*` values.
- **Rejected:** A separate `apps/voice` (`experiment/156`: duplicated env, prompt and types, needed its own Dockerfile). The worker inside the HTTP process (audio and VAD load would share the API's event loop). LiveKit's own LLM plugins (the reply would bypass our LLM setup). Speech-to-speech models like OpenAI Realtime or Gemini Live (no text step between hearing and speaking, so a sentence can't be checked before it is spoken). Pipecat (Python only).
- **Caution:** Nothing checks the replies yet, no real health data until a check exists and the GDPR review (#91) is done. LiveKit Cloud and ElevenLabs receive the audio and text. The backend image carries native LiveKit and ONNX dependencies, with three install scripts allowed in `pnpm-workspace.yaml`. The worker is not deployed: the prod-vm reaches the internet only through the HTW proxy, while WebRTC needs UDP or TURN to LiveKit, and a worker service in `deploy/compose.yml` needs a manual install (`deployment.md`). The LiveKit turn detector model may only be used with LiveKit Agents (LiveKit Model License).
