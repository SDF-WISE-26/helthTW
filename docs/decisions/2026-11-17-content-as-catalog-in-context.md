# AI chat finds content via full catalog in the prompt, ID-only output

- **Status:** proposed· **Date:** 2026-11-17 · **Involved:** @tpiwko @justingebert · **Ref:** #79, #80
- **Decision:** The full catalog (`ID, title, summary` of all items and `ID, name, category, description` of all contacts) goes into the system prompt in a stable order. The frontend sends the catalog with every request, the backend builds the prompt from it. The model writes a short, semi-generic reply and picks relevant content by `itemIds` and `contactIds`. The backend drops unknown IDs, the frontend renders everything else from the content collection within the LLM reply.
- **Why:** Users just had a traumatic experience, so a wrong number or invented advice must be impossible: facts only come from our data. The content stays in the low hundreds, so the prompt is enough and needs no new infrastructure. The model sees all content, so paraphrases like "images in my head during night" can match topics like "bad dreams" - such connections would be hard to establish using fulltext-search or RAGs. The LLM should be able to establish the connections and find suitable infomaterial from the catalog. The catalog is a static prefix, so Gemini's implicit caching should make repeated requests cheaper.
- **Rejected:** Postgres full-text search (vocabulary mismatch without aliases). Embeddings or hybrid (no pgvector yet, see 0004, pipeline effort not justified at this size). Tools for read on demand (extra round trips, less predictable). Model writes the facts with sources (better flow, but free text cannot be verified, can be tested later).
- **Caution:** Caching is best-effort with a minimum prefix size, check cached tokens in the usage data. Tokens grow linearly with content, revisit at about 100 items. Test numbers (hit accuracy, tokens, latency, cache hits) are still missing, its unclear how the chosen approach will perform. Because the catalog comes from the client, anyone calling the API can put their own text into the system prompt. Unknown IDs are still dropped, but the reply text can be steered. Fix by having the backend read `content/` itself (out of scope for this feature, requires bigger rework of content collection).
