# Incident data model

- **Status:** proposed · **Date:** 2026-11-20 · **Involved:** @LilGravyyyy, @behritt · **Ref:** #134, #44
- **Decision:** One table `incidents`, one row per incident. The person sets `date` (required, local date), `time` (optional, local time) and `note` (optional). `account_id` comes from `X-Account-Id` and references `accounts.id` with `onDelete: "cascade"` (0020). `tips_read_at` and `closed_at` are nullable times that the backend sets when the person reports "tips read" or toggles "closed", closing again clears `closed_at`. `id`, `created_at` and `updated_at` are set automatically. Status and progress are derived, not stored: `closed` once `closed_at` is set, otherwise `active`. Progress is a list of steps, at first only "immediate tips read", done once `tips_read_at` is set. With #67, `scheduled_questionnaires` gets an `incident_id`, every scheduled questionnaire of an incident becomes a step and counts as done once a response points to it. The day of an incident ("day 6") is computed from `date`. API sketch, built with #65, #106 and #141 after [`specs/backend.md`](../specs/backend.md): `POST /api/v1/incidents` with `{ date, time?, note? }` creates. `GET /api/v1/incidents` returns `{ items }`, newest first. `GET /api/v1/incidents/:id` returns one. `PATCH /api/v1/incidents/:id` takes any of `date`, `time`, `note`, `closed` (`true`/`false`) and `tipsRead` (`true` only, keeps the first time). `DELETE /api/v1/incidents/:id` returns 204. An incident of another account is always 404. A response holds `id`, `date`, `time`, `note`, `status`, `closedAt`, `steps` (e.g. `[{ "type": "tips", "doneAt": "…" }]`), `createdAt` and `updatedAt`. The note length is limited in the Zod schema (e.g. 1000), not in the database.
- **Why:** Same rule as the questionnaire model (`2026-11-13-questionnaire-format-and-data-model.md`): what can be derived is not stored, so status and progress cannot contradict the times and responses. The ticket asks for questionnaires as later steps, and they only need a column on `scheduled_questionnaires`, `incidents` stays as it is. `date` and `time` are when the incident happened, which can be days before it is recorded, so they are separate from `created_at`. A local date as `date` keeps the day stable across time zones.
- **Rejected:** A `status` column (can disagree with `closed_at`, which also says when). An `incident_steps` table or a JSON `progress` column (would store a questionnaire as done a second time next to its response, and the two can disagree). A table for the days of an incident (the day follows from `date`, content per day comes from `content/`).
- **Caution:** `date`, `time` and `note` are health data: never log them, also not in error messages, and select response fields explicitly. Encrypting the note belongs to #145. #67 decides what happens to an incident's questionnaires when it is deleted or closed. A further manual step (e.g. "talked to someone") would be a new nullable column or its own table, decided by the ticket that adds it.
