# Incident data model

- **Status:** proposed · **Date:** 2026-11-20 · **Involved:** @LilGravyyyy, @behritt, @justingebert, @tpiwko · **Ref:** #134, #44
- **Decision:** `incidents` holds what the person entered and `closed_at`, no status and no progress. Status is `closed` once `closed_at` is set. Steps a person checks off live in `incident_steps` (`incident_id`, `type`, `done_at`), one row per step, created open with the incident and done once `done_at` is set. The first type is `tips` ("immediate tips read"), the allowed types are a Zod list. Questionnaires get no row there: with #67, `scheduled_questionnaires` gets an `incident_id`, and each scheduled questionnaire is a step that is done once a response points to it. The API merges both into one list of steps.
- **Why:** A new kind of aftercare is a new `type`, without a migration. Open steps are in the database, not only in code. A questionnaire's response already says it is done, a second flag could disagree with it (same rule as `2026-11-13-questionnaire-format-and-data-model.md`).
- **Rejected:** A `status` column or a stage enum on the incident (one stage cannot show which steps are done, and it can disagree with them). Questionnaires as rows in `incident_steps` ("done" stored twice). A column per step such as `tips_read_at` (a migration for every new step). A Postgres enum for `type` (a migration for every new type).
- **Caution:** Closing an incident does not depend on its steps, the person decides. A step that happens more than once per incident (e.g. a daily task) needs a further column such as `day` in the unique key. #67 decides what happens to an incident's questionnaires when it is deleted or closed.
